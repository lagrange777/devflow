# Devflow

AI-пайплайн полного цикла разработки небольших изменений Go-приложения: задача → тесткейсы → техническая спецификация → код → подготовка PR → ревью и исправления → релиз.

Это отдельный Go-проект. Он использует тот же контракт доступа к AI, что `codex-chat-cli`: `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`, `OPENAI_TIMEOUT` и `POST /responses`. Исходный проект не меняется, его внутренние Go-пакеты не импортируются. Ключ можно читать прямо из его `.env`: файл не исполняется и не копируется.

## Какую задачу решает приложение

Разработчику приходится повторять одни и те же действия для каждой небольшой функции: сформулировать требования, продумать тесты, написать код, проверить, подготовить PR и выпуск. Devflow выполняет эту последовательность с AI и сохраняет проверяемые артефакты каждого этапа. Go-оркестратор управляет порядком и проверками. AI анализирует задачу, проектирует, пишет файлы, рецензирует diff и исправляет замечания.

Первая версия рассчитана на небольшие существующие Go-приложения со стандартной библиотекой и одним исполняемым main-пакетом. Расширять зависимости и менять инфраструктуру в этом MVP нельзя.

## Быстрый запуск

Нужны Go 1.25+, Git. По умолчанию проверки выполняются в Docker с образом `golang:1.25`. Для публикации дополнительно нужны `gh`, доступ к origin GitHub и настроенная авторизация `gh auth login` либо `GH_TOKEN`/`GITHUB_TOKEN` в окружении.

```bash
git clone https://github.com/lagrange777/devflow.git
cd devflow
go build -o bin/devflow ./cmd/devflow

# Проверяет реальный API маленьким запросом, не показывает ключ.
./bin/devflow doctor --env-file ../codex-chat-cli/.env

# Создаёт отдельный учебный Git-репозиторий, не перезаписывает существующий.
./scripts/prepare-demo.sh

./bin/devflow start \
  --repo "$PWD/demo/hello" \
  --env-file ../codex-chat-cli/.env \
  --task 'Добавь GET /hello?name=...: без имени Hello, world!; с именем Hello, <name>!; максимум 40 Unicode-символов, более длинное имя возвращает HTTP 400. Сохрани существующее поведение без параметра.'
```

Учебный сервис из `examples/hello` слушает порт 18080, чтобы не пересекаться со стандартным портом `codex-chat-cli`.

Каждый запуск создаёт новую ветку `codex/devflow/<id>` и отдельный Git worktree внутри `runs/<id>/worktree`. Исходная рабочая копия остаётся на прежней ветке. Каталог запуска обязательно располагается вне целевого репозитория. Перед стартом целевой репозиторий должен быть чистым.

Если Docker недоступен, добавьте `--runner local`. Этот режим запускает сгенерированный Go-код с правами вашего пользователя и подходит для доверенного учебного репозитория. В Docker контейнер ограничен по памяти/CPU/процессам, не получает API-ключи, работает без сети и с доступом на запись только к своей рабочей копии и временному каталогу. Это ограничение контейнера, а не гарантия абсолютной изоляции недоверенного кода.

Для main-пакета в подкаталоге передайте `--package ./cmd/server`. Целевой модуль должен собираться без добавления зависимостей; в Docker зависимости из локального Go-кеша не доступны.

## Состояние и продолжение

```bash
./bin/devflow status --run runs/<id>
./bin/devflow resume --run runs/<id> --env-file ../codex-chat-cli/.env

# Если AI задал блокирующий вопрос:
./bin/devflow resume --run runs/<id> \
  --env-file ../codex-chat-cli/.env \
  --answer 'Лимит — 40 Unicode-символов; пробелы сохраняем.'
```

`awaiting_input` требует ответа. `failed` позволяет повторить текущий этап после исправления внешней причины, например отсутствующей авторизации. После исчерпания общего бюджета доработок состояние становится `blocked`: изучите отчёты и начните новую, уточнённую задачу. `awaiting_release` означает, что весь AI-процесс завершён и ожидается одобрение выпуска.

JSON-состояние записывается атомарно, один запуск защищён файловой блокировкой. Скиллы и правила копируются в неизменяемый снимок запуска; артефакты проверяются по SHA-256 при продолжении. Во время работы не редактируйте worktree, артефакты или `run.json` вручную. Это локальный инструмент для одного доверенного пользователя, не многопользовательская система с криптографически защищённым журналом.

## Этапы, AI и проверки

| Этап | Работа AI | Проверка Go-оркестратора |
|---|---|---|
| `clarify` | Критерии приёмки, предположения, вопросы | Критерии непустые, ID уникальны; при вопросах остановка |
| `test_cases` | Позитивные, негативные и граничные сценарии | Покрыты все критерии; сценарии связаны с будущими Go-тестами |
| `specification` | API, ошибки, совместимость, список файлов | Явный допустимый список файлов, включающий все тестовые файлы |
| `implementation` | Полные новые версии файлов | Контроль путей, `gofmt`, `go vet`, `go test`, `go build`; проверка выполненных тестов |
| `pull_request` | Описание проблемы, изменений и проверок | Проверенный коммит; локальный PR-документ или настоящий draft PR |
| `review` | Отдельный запрос с diff, требованиями, кодом и логами | Блокирующие замечания возвращают в реализацию; после доработок новое ревью |
| `release` | Release notes | Привязка к проверенному SHA и дереву, ожидание явного одобрения |

Связь сценария с автоматическим тестом проверяется по AST конкретного `_test.go` и событиям `go test -json -count=1`: должен выполниться и пройти тест с указанным именем в нужном Go-пакете. Это подтверждает факт выполнения. Смысл и достаточность утверждений проверяет AI-ревью; формальной гарантии корректности AI не даёт.

Все вызовы модели независимы, получают входные артефакты явно, используют JSON Schema и `store: false`. Отказы, незавершённые ответы и невалидные документы останавливают этап. Нет скрытых повторов HTTP-запросов. Модель берётся из настроек исходного проекта; подмена модели не выполняется.

## Скиллы и инварианты

Встроенные инструкции находятся в `assets/skills/<stage>/SKILL.md`, правила — в `assets/invariants.json`. Для своих инструкций:

```bash
./bin/devflow init --dir my-rules
# Измените my-rules/skills/*/SKILL.md и my-rules/invariants.json.
./bin/devflow start --rules my-rules --repo /absolute/path/to/repo \
  --env-file ../codex-chat-cli/.env --task '...'
```

Можно менять скиллы, бюджет исправлений, лимиты контекста/файлов и таймаут команд. Базовые проверки порядка этапов, путей, фактического выполнения тестов и одобрения SHA реализованы в Go. Поле `rules` даёт AI человекочитаемые инструкции; добавление строки само по себе не создаёт новую программную проверку. Для нового типа инварианта требуется добавить валидатор в код.

Перед проверками Devflow автоматически форматирует сгенерированные `.go` файлы средствами `go/format`. Синтаксические ошибки передаются в обычный цикл проверок и доработок.

AI может менять только согласованные `.go` файлы и `README.md`. Изменения зависимостей, секретов, скрытых каталогов, CI, Git и симлинков запрещены. Ключи AI не попадают в run state, prompts или окружение запускаемых команд; для `gh` передаётся только его собственный токен, если он задан в окружении. В AI отправляется исходный код целевого модуля: выбирайте репозитории, которые можно передавать вашему API-провайдеру.

## Локальный релиз

После `awaiting_release` возьмите полный `reviewed_sha` из `status` и выполните:

```bash
./bin/devflow release --run runs/<id> \
  --approve-sha FULL_REVIEWED_SHA --version v0.1.0
```

Devflow повторяет проверки и собирает архив с исполняемым файлом, manifest, SHA-256 и локальным Git-тегом. Результаты — в `runs/<id>/dist`. При Docker-сборке бинарник предназначен для Linux, при local — для ОС запуска. Docker-образ приложения и развёртывание на сервер в этой версии не выпускаются.

Локальный режим не требует GitHub и позволяет показать весь цикл от реального AI до запуска собранного бинарника. Команда `release` является явным одобрением конкретного SHA. Выпустить другой коммит или версию незавершённого запуска нельзя.

## Настоящий GitHub PR и релиз

```bash
./bin/devflow start \
  --repo /absolute/path/to/go-repo \
  --env-file ../codex-chat-cli/.env \
  --publish --github-repo owner/repository --base main \
  --task '...'
```

`--publish` разрешает push ветки и создание draft PR. `origin` обязан соответствовать указанному GitHub-репозиторию. После исправления замечаний и успешного ревью обновлённая ветка отправляется в origin, PR становится ready for review.

Слияние PR выполняет человек в GitHub. Перед публикацией релиза сервис требует merged PR с тем же head SHA и успешные обязательные GitHub checks (как минимум один). Настройте required checks в целевом репозитории. После слияния выполните ту же команду `release --approve-sha ... --version ...`: она создаст тег и GitHub Release с архивом и контрольными суммами. Тег указывает на одобренный feature-коммит; при squash merge SHA в основной ветке будет другим.

Публикация не проверялась на пользовательском GitHub без конкретного разрешённого целевого репозитория. Повтор после прерывания сверяет PR по ветке и SHA тега; повтор выпуска с теми же SHA/версией безопасен. Для нескольких параллельных запусков используйте разные версии релиза.

## Артефакты запуска

- `run.json` — состояние, SHA, история этапов, расход токенов и длительность AI-вызовов.
- `rules/` — снимок скиллов и инвариантов.
- `request-*.json` — точные инструкции, контекст и схема запроса без ключа.
- `NNN-<stage>.json` — результаты AI, включая итерации исправлений.
- `checks-*.log`, `release-checks.log` — настоящие результаты команд.
- `pull-request.md`, `release-notes.md` — готовые материалы для PR и релиза.
- `worktree/` — код и отдельная ветка задачи.
- `dist/` — архив, manifest и контрольные суммы.

Запуски и бинарники исключены из Git. Worktree сохраняется для исследования; после сохранения нужных результатов удалите его обычным `git worktree remove /path/to/run/worktree`. Ветка задачи сохраняется в целевом Git-репозитории.

## Проверки самого Devflow

```bash
go test ./...
go vet ./...
go build ./cmd/devflow

# Дополнительная проверка настоящего изолированного Docker-runner:
DEVFLOW_TEST_DOCKER=1 go test ./internal/flow -run TestDockerChecks -v
```

Сквозные тесты используют управляемую модель, настоящий Git, настоящие Go-проверки и сборку релиза. Они проверяют порядок, вопросы/ответы, цикл исправлений, привязку тестов, блокировки, изменение артефактов, запрещённые пути и одобрение SHA. Контракт API проверяется HTTP-транспортом без ключей и сетевого доступа.

## Структура

```text
cmd/devflow/       CLI
internal/ai/       Responses API-клиент
internal/config/   чтение настроек AI из окружения или codex-chat-cli/.env
internal/flow/     машина состояний, проверки, Git, GitHub, сборка релиза
assets/skills/    инструкции семи этапов
assets/invariants.json
examples/hello/   учебный Go HTTP-сервис
scripts/          подготовка отдельного демонстрационного репозитория
```

Формат AI-запросов сверён с официальной документацией: https://developers.openai.com/api/docs/guides/structured-outputs
